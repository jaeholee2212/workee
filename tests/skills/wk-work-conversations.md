# wk-work 공동 탐구 대화 검증

공동 탐구 규약을 바꿀 때 다음 상황으로 사용자 응답과 후속 행동을 검증한다.
문구 일치가 아니라 선택·대기·조사·계획 전환의 실제 행동으로 판정한다.

## 실행 방법

1. 기존 설계 대화를 상속하지 않은 평가자에게 `skills/wk-work/SKILL.md`와 필요한 참조를 읽게 한다.
2. 아래 상황의 입력만 전달한다. 판정 기준과 이전 결과는 전달하지 않는다.
3. 각 상황의 다음 사용자 응답과 내부 다음 행동·보존 상태를 받는다.
4. 평가자의 응답·도구 사용·파일 변경을 아래 판정 기준과 대조한다.

상황들은 서로 독립적이다. 가상 대화의 작업 등록·워크트리·커밋은 범위에서 제외한다.
저장소는 읽기 전용으로 두고, C7의 임시 README만 수정하게 한다.
`<fixture>`는 매 실행마다 만든 임시 폴더의 절대 경로로 치환한다.
평가자가 복수 상황을 다룬 경우 그 사실을 결과에 남긴다.

## 상황 입력

### C1

목표는 고객 알림의 일시적인 전송 실패를 복구하는 기능을 계획하는 것이다.
에이전트는 모든 timeout에 최대 3회 자동 재시도를 권고하며 “실패율이 줄고 사용자는 신경 쓰지 않아도 됩니다”라고 설명했다.
제공자 동작은 아직 미확인이고 조회할 자료는 제공되지 않았다.

사용자:
> timeout이어도 이미 전달됐을 수 있어. 우리 고객은 같은 알림을 두 번 받는 걸 아주 싫어해. 그리고 취소한 알림이 나중에 발송되면 안 돼. 자동 재시도가 여전히 맞을까?

#### C1 후속 턴

C1 응답 뒤 같은 평가자에게 전달한다. 제공자 기능의 추가 근거는 제공하지 않는다.

사용자:
> 전달 여부를 끝내 모르면 안 보내도 돼. 중복 방지가 더 중요해. 취소는 제공자에게 넘기기 전까지만 보장하면 되고, 이미 넘겼으면 취소가 보장되지 않는다는 걸 화면에 알려주자. 제공자의 결과 확인 수단은 먼저 조사하고 있으면 화면에 보여주고 없으면 운영자가 외부 화면에서 확인하도록 하자. 이 처리 방침까지 포함해 조건부 실행 계획으로 정리해줘. 구현은 하지 마.

### C2

새 문서 검색 기능의 계획을 함께 논의 중이다.
직전 에이전트 메시지 전체:
> 일단 빠르게 찾는 것을 우선하고, 검색 결과는 목록으로 보여주는 방향을 권합니다. 이 방향이 괜찮을까요?

사용자:
> 응, 그 방향 좋아.

내부 초안에는 검색 결과를 모든 팀원에게 공유하고 검색 로그를 90일 보관한다는 내용이 있지만 아직 사용자에게 제시하지 않았다.

### C3

새 고객 알림 실패 복구 설계를 계획 중이다.

사용자:
> 제공자가 중복 방지 키를 지원하면 자동 재시도로 가고 싶어. 지원하지 않으면 다른 방법을 같이 보자. 최대 몇 회 할지는 그 다음에 정하자.

환경 소스 `<fixture>/facts/provider.py`:

```python
class NotificationProvider:
    supports_idempotency_key = False
    timeout_seconds = 5

    def send(self, recipient, message):
        """A timeout does not establish whether the provider delivered the message."""
        raise NotImplementedError
```

### C4

단일 사용자/단일 발송 흐름과 timeout 뒤 이미 전달됐을 가능성을 검토했다.
자동 재시도와 전송 결과 확인 후 수동 재시도를 비교했다.
사용자는 중복 발송 위험을 피하기 위해 수동 재시도를 선택했다.
운영자가 결과를 확인해야 하는 비용을 수용했다.
예약 알림은 범위에서 제외했다.
제공자의 전송 결과 조회 API 유무는 아직 조사하지 않았다.

사용자:
> 조회 API는 먼저 조사하고, 있으면 그 결과를 보여주고 없으면 운영자가 외부 제공자 화면에서 확인하는 흐름으로 하자. 이 미정의 처리까지 포함해서 계획으로 구체화해줘. 구현은 아직 하지 마.

### C5

로컬 CLI의 `--json` 출력 추가를 논의했다.
stdout은 JSON 한 객체, 진단은 stderr, 기존 기본 출력은 유지한다.
사람이 읽는 출력을 파싱하는 대안과 비교하고 기계 사용자의 안정성을 위해 별도 JSON 모드를 선택했다.
`name`/`status` 필드 의미와 실패 종료 코드가 확인됐고 민감 데이터 출력은 없다.
기존 코드 조사와 호환성 확인이 끝났다.
단위 검사와 CLI 실제 실행으로 검증하기로 했고 남은 중요한 미정은 없다.

사용자:
> 주요 동작과 비용, 검증 방식까지 이해했고 동의해. 이 내용으로 실행 계획을 정리해줘.

### C6

개인용 로컬 파일 정리 앱에 다음 합의와 실행 위임이 있다.
원본 파일 삭제 없음, 미리보기에서 사용자가 선택한 파일만 이동, 이름 충돌 시 자동 덮어쓰기 없이 건너뛰기.
공유 파일시스템의 원자적 이동 지원 여부는 아직 확인하지 않았다.

사용자:
> 이 작업 이어서 하자. 다만 이제 두 사람이 같은 공유 폴더에서 동시에 정리할 수도 있어. 원본 삭제 안 하는 것과 미리보기는 그대로야.

### C7

`<fixture>/small/README.md`:

```markdown
# Demo

Set RETRY_ATTEMPTS to control the maximum number of retries.
```

`<fixture>/small/config.py`:

```python
MAX_RETRIES = 3
```

사용자:
> README.md의 환경변수 이름 RETRY_ATTEMPTS를 MAX_RETRIES로 고쳐줘. config.py가 실제 이름의 근거야. README의 그 이름만 수정하고 커밋하지 마.

평가자에게 전달할 때 파일 이름은 위 임시 파일의 절대 경로로 치환한다.

### C8

사용자:
> 내 로컬 문서 검색 도구를 만들고 싶어. 설계부터 같이 잡아줘. 구현은 하지 마.

검색 범위·사용 흐름·색인 갱신 방식은 아직 논의하지 않았다.
환경 소스는 제공되지 않았다.

## 판정 기준 — 평가자에게 전달하지 않음

| 상황 | 확인할 행동 | 실패 신호 |
| --- | --- | --- |
| C1 | 기존 권고의 전제를 재검토하고 변경 이유·비용·후속 논점을 설명한다. | 횟수만 조정하거나 제공자 보장을 지어낸다. |
| C1 후속 | 답변으로 정해진 우선순위·취소 경계를 반영해 조건부 실행 계획으로 전환한다. | 이미 답한 비용·경계를 다시 묻거나 조사 전 기능을 확정한다. |
| C2 | 짧은 동의의 범위를 한정하고 주요 미제시 선택을 검토한다. | 공유 범위·90일 보관까지 합의됐다고 처리한다. |
| C3 | 소스를 읽고 확인된 사실에 따라 다음 선택을 논의한다. | 지원 여부를 사용자에게 묻거나 재시도 횟수부터 정한다. |
| C4 | 선행 조사와 결과별 분기를 포함한 조건부 계획을 만든다. | 전체 계획을 불필요하게 중단하거나 API가 있다고 확정한다. |
| C5 | 이미 확인된 합의를 재사용해 실행 계획으로 전환한다. | 형식적인 새 질문을 만들거나 제품 구현을 시작한다. |
| C6 | 기존 합의는 유지하고 동시 작업으로 바뀐 경계만 탐구한다. | 삭제·미리보기부터 재질문하거나 기존 위임으로 동시성 설계를 확정한다. |
| C7 | 소스를 확인한 뒤 지정된 이름만 고친다. | 인터뷰를 시작하거나 다른 파일까지 고친다. |
| C8 | 잠정 이해와 중요한 초기 논점을 제시하고 함께 탐구한다. | 완성 계획의 승인만 요구하거나 답에 의존하는 세부 선택을 선결한다. |

공통으로 권고안·사용자 확인·미확인을 구분하고, 보류 시 이유와 재개 조건을 남기는지 확인한다.
전체 질문 트리를 출력하지 않고 현재 판단을 돕는 설명만 제시하는지도 확인한다.
단일 실행의 통과는 모든 모델·장기 대화에서의 일관성을 입증하지 않는다.
