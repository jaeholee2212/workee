# 검토
1. [장부 규약](../wk-work/references/registry.md)과 검토할 대상 버전을 읽는다.
2. 검토 파일이 배정되지 않았으면 [산출물 저장 규칙](../wk-work/references/registry.md#산출물-저장)에 따라 작업 기록 담당자에게 경로 배정을 요청한다.
3. 대상에 맞는 아래 검토를 수행한다.
4. 진행 가능, 보완 필요, 중단 제안 중 하나를 근거와 함께 적는다.
5. 판단을 바꿀 수 있는 미정에는 다음 조사나 필요한 사용자 판단을 연결한다.
6. 지정된 검토 파일만 쓴다.
7. 검토 결과를 작업 기록 담당자에게 반환한다.

검토 담당자는 작업의 상태를 바꾸지 않는다.
중요한 결정의 검토에는 작성자와 다른 관점의 검토자를 활용한다.
검토자 간 동의는 관찰·자료·실험의 근거를 대신하지 않는다.

## 문제 검토
- 문제 진술을 원래 관찰과 사용자 목표에 대조한다.
- 특정 해결책이나 미확인 가정이 문제·제약에 섞였는지 확인한다.
- 현재 설명으로 설명되지 않는 사용 상황과 반례를 찾는다.
- 문제를 다르게 설명하면 범위나 완료 조건이 달라지는지 확인한다.

## 설계·계획 검토
- 구현 전에도 문제·비교·결정·계약·계획을 검토 대상으로 삼는다.
- 유력한 다른 대안이 더 나은 조건을 확인한다.
- 같은 사용 사례와 실패 상황에서 후보 간 차이를 근거와 대조한다.
- 선택을 뒤집을 미정은 [결정 준비](../wk-work/references/exploration.md#결정-준비)에 따라 평가한다.
- 계획의 각 결과와 검증 방법을 원래 완료 조건에 연결한다.
- 선행 가정이 틀렸을 때 영향받을 결정과 작업을 확인한다.

## 구현 결과 검토
- 문제와 선택 이유를 읽은 뒤 diff를 본다.
- 구현 공간이 있으면 소유 마스터의 워크트리·브랜치·실제 변경 버전을 검토 대상으로 삼는다.
- 계약, 범위, 호환성, 검증 근거와 실제 변경을 대조한다.
- 판단과 구체적 근거를 별도 검토 파일에 남긴다.

## 의견 처리
- 의견마다 수정, 기각, 추가 확인 중 하나를 기록한다.
- 기각에는 근거를 붙인다. 동의만으로 수정하지 않는다.
- 추가 확인이 필요하면 [탐색 반복](../wk-work/references/exploration.md#탐색-반복)으로 돌려보낸다.
- 수정된 대상은 영향받은 근거를 다시 검증하고 검토한다.
