# 공동 탐구

`wk-work`가 논의·계획에서 사용자와 문제·대안·설계를 함께 발전시킬 때 읽는다.
목표는 서로의 제안과 전제를 검토하며 처음보다 나은 방향을 만드는 것이다.
기존 합의의 재사용과 실행 권한은 [진행 정책](progression.md#자율-진행과-사용자-판단)을 따른다.

## 적용 범위

- 새 목표나 주요 설계 변경에는 공동 탐구를 기본으로 시작한다.
- 재개할 때는 기존 이해를 복원하고 달라진 부분만 탐구한다.
- 대상과 동작이 명확한 작은 수정은 기존 지시로 진행한다.
- 조사 중 주요 설계 문제가 드러나면 영향받는 논점을 연다.

주요 설계는 문제 정의·주요 사용 흐름·책임과 데이터 경계·운영 부담·되돌리기 비용을 바꾸는 선택이다.
파일 수나 구현 난이도만으로 중요도를 정하지 않는다.
주요 설계는 에이전트가 권고안을 알고 있어도 사용자와 판단 근거를 함께 검토한다.
합의한 방향 안의 사소한 구현 선택은 위임 범위에서 처리한다.
사용자가 설계 선택까지 명시적으로 맡기거나 초안·조사만 요청한 경우는 [요청 범위와 위임](progression.md#합의와-실행-위임)을 우선한다.

## 대화와 탐색의 반복

1. 직접 확인한 사실·사용자가 전달한 경험·현재 해석을 구분한다.
2. 초기 해석이 바뀔 수 있을 때 문제와 잠정 접근을 사용자에게 제시한다.
3. 주요 논점과 선행 관계를 [탐구 논점](../references/work-model.md#탐구-논점)에 정리한다.
4. [질문 선택](#질문-선택)으로 지금 다룰 논점을 골라 [함께 검토](#함께-검토할-내용)한다.
5. 답변에서 새로 드러난 전제·선택·예외와 기존 해석의 충돌을 찾는다.
6. 새롭게 알게 된 점과 바뀌거나 유지한 판단의 이유를 사용자에게 설명한다.
7. 답변으로 열린 질문과 무효화된 전제에 맞춰 논점의 의존 관계를 갱신한다.
8. 다음 입력이 사실이면 조사·비교·실험을 배정하고, 사용자 판단이면 다음 대화를 연다.
9. [탐구 완료](#탐구-완료)의 근거와 남은 논점으로 반복 여부를 판단한다.

진척은 새롭게 공유한 이해와 그로 인해 달라지거나 근거가 보강된 문제·기준·선택으로 확인한다.
사용자 피드백과 그 영향은 [공동 검토 기록](../references/work-model.md#공동-검토와-실행-위임)에 연결한다.
응답을 기다릴 때는 [질문과 대기](progression.md#질문과-대기)에 따라 독립적인 조사를 이어 간다.

## 질문 선택

- 선행 답변이나 조사 결과 없이 판단할 수 있는 논점 중 설계를 바꿀 가능성과 잘못 판단할 비용이 큰 것을 먼저 다룬다.
- 답변에 의존하는 후속 질문은 그 답변을 받은 뒤 다시 구성한다.
- 질문에는 답에 따라 달라질 판단과 지금 다룰 이유를 연결한다.
- 아직 표현되지 않은 요구를 찾을 때는 실제 사용 사례에서 목표·장애물·실패 상황을 따라간다.
- 코드나 자료로 확인할 사실은 직접 조사한다.
- 사용자의 경험·선호·비용 수용은 사용자와 검토한다.
- 중요한 논점을 뒤로 미루면 이유와 다시 다룰 조건을 짧게 알린다.
- 사용자가 새 논점을 제시하거나 우선순위를 바꾸면 현재 질문 구조를 다시 잡는다.

질문 묶음은 한 번에 함께 판단할 수 있는 범위로 정한다.
질문 수나 라운드 수를 고정하지 않는다.
모든 가지를 방문하거나 사소한 구현 선택까지 질문하는 것을 완료 조건으로 삼지 않는다.

## 함께 검토할 내용

| 대상 | 대화에 가져올 내용 |
| --- | --- |
| 문제 | 관찰한 현상·사용자의 실제 경험·가능한 다른 설명·해결할 문제와 제외 범위 |
| 대안 | 같은 사용 사례에서의 차이·판단 기준·강한 반대안·권고안이 불리해지는 조건 |
| 설계 | 주요 사용 흐름·실패 상황·책임과 데이터 경계·사용자 행동과 운영 부담의 변화 |
| 실행 계획 | 합의한 설계를 구현할 단위·선행 조건·검증 방법·남은 위험·위임할 실행 범위 |

사용자 제안과 에이전트 권고안 모두의 전제·용어의 의미·일관성을 검토한다.
주요 설계에서는 권고안이 실패하는 조건과 유력한 반대안이 더 나은 조건을 능동적으로 찾는다.
반박에는 구체적인 사례나 근거를 붙인다.
비교 과정에서 더 나은 접근이 드러나면 후보 자체를 수정하거나 추가한다.
형식적인 반대안을 채우는 대신 실제 선택을 가르는 차이를 확인한다.
반례를 검토한 뒤 기존 방향을 유지해도 그 이유가 더 선명해졌다면 진척으로 기록한다.

## 논점 제시

- 전체 방향·이번에 달라진 이해·다음 핵심 논점을 짧게 공유한다.
- 관찰·현재 해석·불확실성·질문의 이유를 짧게 연결한다.
- 선택이 필요하면 실제 차이와 권고 근거를 함께 제시한다.
- 비교가 어려우면 같은 사용 사례를 따라가는 예시·표·작은 도식으로 차이를 드러낸다.
- 전체 질문 구조는 기록으로 유지하고, 대화에는 현재 판단에 필요한 부분을 펼친다.
- 사용자가 질문·반례·새 대안을 보태거나 문제 정의를 바꿀 여지를 남긴다.
- 권고안과 사용자 답변으로 실제 확인된 내용을 구분한다.

기술 용어는 현재 판단에 필요한 뜻을 설명한다.

## 탐구 완료

요청 범위의 주요 선택마다 다음 근거가 갖춰지면 탐구 결과를 정리한다.

- 문제와 주요 사용 사례에 대한 해석을 함께 검토했다.
- 선택한 방향의 이유·유력한 반대안을 택하지 않은 이유·중요한 실패 조건과 감수할 비용을 검토했다.
- 설계를 바꿀 남은 불확실성마다 조사·보류·수용·위임의 처리 방법과 영향을 정했다.
- 보류한 논점에는 이유와 다시 다룰 조건이 있다.

문제·선택과 이유·비용·남은 불확실성과 처리 방법을 짧게 요약해 같은 이해에 도달했는지 확인한다.
실제 대화에서 이미 확인된 범위는 그 근거를 재사용한다.
사용자가 납득하지 못한 부분이 있으면 해당 논점을 다시 연다.
완료 근거가 갖춰졌으면 새 질문을 억지로 만들지 않고 요청된 다음 결과로 이어 간다.
불확실성의 처리 합의는 그에 의존하는 실행의 준비 완료를 뜻하지 않는다.
선행 조사가 남은 구현은 조건부로 두고 결과에 따른 분기를 계획에 전달한다.

## 전환과 재개

단계 전환 시 [합의와 실행 위임](progression.md#합의와-실행-위임)을 확인한다.
새 근거나 사용자 의견이 기존 합의를 바꾸면 [합의 변경과 재검토](progression.md#합의-변경과-재검토)를 적용한다.
