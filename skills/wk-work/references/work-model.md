# 공통 작업 모델

스킬 실행 결과와 작업의 항목·관계·상태·검증 근거·완료 판정을 정의한다.
작업 ID와 문서 갱신 방법은 [장부 규약](registry.md)을 따른다.

## 스킬 실행 결과

하위 스킬은 맡은 결과를 만든 뒤 다음 내용을 반환한다.
작은 결과는 짧은 문장으로 표현할 수 있다.
표현 형식이나 별도 보고서 수를 고정하지 않는다.

| 항목 | 내용 |
| --- | --- |
| 요청한 결과 | 이번 실행이 맡은 질문이나 산출물 |
| 수행 상태 | 완료·보완 필요·진행 불가 중 하나와 그 근거 |
| 결과와 근거 | 확인한 사실·판정·산출물 위치·대상 버전 |
| 남은 미정 | 확인하지 못한 내용·결론에 미칠 영향·필요한 입력이나 판단 |

- 완료는 해당 스킬의 자기 결과가 완료 기준을 충족했다는 뜻이다.
- 보완 필요는 결과가 있으나 완료에 필요한 근거나 입력이 부족하다는 뜻이다.
- 진행 불가는 현재 접근·권한·선행 조건으로 맡은 결과를 더 만들 수 없다는 뜻이다.
- 검토·검증 수행이 완료됐어도 대상의 판정은 실패나 판단 불가일 수 있다.
- 수행 상태는 [작업 상태](#단계와-상태)나 [검증 판정](#검증-근거)을 대신하지 않는다.
- 다른 스킬이 필요한 미정은 필요한 결과와 근거로 반환한다.
- `wk-work`는 반환값으로 다음 스킬·단계·질문과 전체 상태를 정한다.
- 하위 스킬은 전체 작업의 상태를 임의로 바꾸지 않는다.
- 직접 요청받은 스킬은 맡은 결과의 수행 상태를 응답한다.

## 작업 단위와 용어

| 용어 | 의미 |
| --- | --- |
| 작업 | 목표와 완료 조건을 가진 결과 단위 |
| 마스터 작업 | 하위 작업을 가지며 전체 목표와 결과의 합류를 책임지는 작업 |
| 하위 작업 | 상위 작업의 완료 조건에 기여하는 결과를 책임지는 작업 |
| 최상위 작업 | 상위 작업이 없는 작업 |

작은 목표는 하위 작업 없이 하나의 작업으로 진행한다.
논의·계획·구현·검증이라는 단계 이름만으로 하위 작업을 만들지 않는다.
스킬은 수행 방법이고 서브에이전트는 결과를 맡는 실행자다.
서브에이전트 수만큼 하위 작업을 만들지 않는다.

## 현재 기록

`work.md`에 다음 공통 항목을 기록한다.

| 항목 | 내용 |
| --- | --- |
| 목표 | 해결할 문제나 얻을 결과 |
| 범위·제외 | 이번에 다루는 것과 다루지 않는 것 |
| 완료 조건 | 결과를 판정할 관찰 가능한 조건 |
| 단계 | 다음 행동에 해당하는 논의·계획·구현·검증 |
| 상태 | 아래 상태 중 하나 |
| 상위 작업 | [포함 관계](#포함-관계)에 따른 상위 표시 |
| 담당자 | 현재 기록·실행 담당자 또는 미정 |
| 산출물·검증 | 결과 링크·확인한 버전·[검증 근거](#검증-근거) |
| 다음 행동 | 다음 실행이나 필요한 선택 |

- 미정인 목표·범위·완료 조건은 미정으로 적는다.
- 진행을 막는 미정은 다음 행동으로 연결한다.
- 하위 작업이 있으면 ID·링크·전체 완료 조건에 기여할 결과를 덧붙인다.
- 선행 산출물이 있으면 제공 작업·링크나 예정 위치·준비 조건·소비 시점·준비 여부의 근거를 덧붙인다.
- 위임한 결과가 있으면 실행자 식별자·맡은 결과·작성 범위·최근 진행·회수한 결과 위치를 연결한다.
- 커밋할 변경이 있으면 [커밋 후보](#커밋-후보)와 확정 SHA·검증 근거를 연결한다.
- 불필요한 빈 하위 작업 목록이나 의존성 표는 만들지 않는다.

## 현재 이해

논의·계획에서 가설이나 대안을 다루면 `work.md`에 현재 이해를 요약한다.
아래 항목 중 판단에 필요한 내용만 남긴다.
작은 작업은 한 단락으로 기록할 수 있다.

| 항목 | 내용 |
| --- | --- |
| 문제와 근거 | 현재 문제 설명, 직접 확인한 사실과 출처·대상 버전, 전달받은 보고 |
| 가정과 미정 | 아직 확인하지 않은 설명·제약, 확인 결과가 판단에 미칠 영향 |
| 후보와 비교 | 유력 후보의 차이, 제외한 후보와 그 근거, 아직 확인할 비교 기준 |
| 결정 | 선택과 감수할 비용, 사용자 판단·위임된 기술 판단·제안의 구분, 재검토 조건 |
| 다음 질문 | 선택을 바꿀 수 있는 질문, 확인 방법, 지금 조사할 이유 |

- 세부 근거는 유효한 산출물에 연결한다.
- 하위 스킬은 새 근거와 판단에 미친 영향을 반환한다.
- `wk-work`는 반환된 근거로 현재 이해를 통합한다.
- 작업 기록 담당자는 통합한 현재 이해를 갱신한다.
- 스킬을 직접 요청받았으면 배정된 기록 범위 안에서 해당 결과를 반영한다.
- 판단을 바꿨거나 유지한 이유는 `history.md`에 남긴다.
- 새 근거가 판단의 전제를 깨뜨리면 영향받는 결정·계약·계획을 재검토 대상으로 표시한다.
- 전제가 무효인 산출물은 현재 유효본에서 제외한다.
- 이전 산출물은 [확정·수정·참조 규칙](registry.md#확정수정참조)에 따라 보존한다.
- 결정의 권한은 [자율 진행과 사용자 판단](../policies/progression.md#자율-진행과-사용자-판단)을 따른다.

## 단계와 상태

상태는 다음 행동을 진행할 수 있는지와 작업이 끝났는지를 나타낸다.
예를 들어 `단계: 구현`, `상태: blocked`를 함께 기록할 수 있다.

| 상태 | 의미 |
| --- | --- |
| pending | 등록했지만 실행을 시작하지 않았다. |
| active | 현재 진행 중이다. |
| blocked | 필요한 산출물·결정·권한 등이 없어 진행할 수 없다. |
| paused | 의도적으로 중단했고 담당자의 쓰기가 끝났다. |
| done | 이 문서의 완료 판정을 충족했다. |
| canceled | 명시적으로 하지 않기로 했다. |

- blocked와 paused에는 사유와 재개 조건을 기록한다.
- 재개할 때는 현재 근거로 단계와 상태를 다시 판단한다.
- 마스터 작업의 단계·상태를 하위 작업에 복사하지 않는다.
- 완료 후 관련 변경이나 미충족 조건이 발견되면 영향받는 작업을 다시 연다.
- 재개와 완료 판정 변경의 이유는 이력에 남긴다.

## 포함 관계

- 상위 작업은 없거나 하나이며, 없음 또는 ID·`work.md` 링크로 표시한다.
- 자기 자신이나 자손을 상위 작업으로 지정하지 않는다.
- 연결할 작업 ID와 파일이 실제로 존재하는지 확인한다.
- 하위 작업의 상위 작업 필드와 마스터 작업의 하위 작업 목록을 맞춘다.
- 관계를 바꾸면 양쪽 작업의 이력에 이유를 남긴다.
- 기존 작업을 연결할 때는 그 목표가 상위 작업의 완료 조건에 기여하는지 확인한다.
- 관련 작업과 범위 분리의 출처는 별도 링크로 유지한다.
- 다른 구현 작업공간을 사용하는 작업의 상위를 바꾸려면 기존 변경의 보존·합류 방법부터 확인한다.
- 관계 변경만으로 코드나 워크트리를 이동하지 않는다.

## 선행 산출물

의존성은 특정 행동에 필요한 산출물과 준비 조건을 나타낸다.

- 포함 관계만으로 의존성을 만들지 않는다.
- 제공 작업의 done 여부와 무관하게 산출물의 실제 준비 조건으로 소비 가능 여부를 판단한다.
- 산출물이 없거나 유효하지 않으면 그것을 소비하는 행동만 대기시킨다.
- 같은 작업끼리 주고받는 산출물은 소비 시점을 구분한다.
- 실제 산출물의 선행 관계에 순환이 있으면 진행 전에 고친다.
- 제공 작업이 done이어도 파일·계약·외부 자원 충돌은 별도로 확인한다.
- 다른 소유 작업의 코드 산출물은 현재 워크트리에 필요한 버전이 실제로 반영됐는지 확인한다.

예를 들어 A의 접점 합의로 B가 handler를 만들고, A가 그 handler를 최종 연결에 사용할 수 있다.

## 구현 작업공간

- 최상위 작업을 전용 브랜치·워크트리 하나의 소유 작업으로 정한다.
- 모든 하위 작업은 소유 작업의 브랜치·워크트리를 공유한다.
- 구현 작업공간 정보의 원본은 소유 작업의 `work.md`다.
- 하위 작업에는 소유 작업 링크를 기록한다.

구현을 시작할 때 소유 작업에 다음 정보를 기록한다.

| 항목 | 내용 |
| --- | --- |
| 저장소 | 절대 경로로 확인한 Git 공통 디렉터리 |
| 기준 | 원본 작업공간·기준 브랜치·전체 커밋 ID |
| 설정 원본 | 공유 장부를 가리키는 `wk-factory.yaml`의 절대 경로 |
| 작업 브랜치 | 소유 작업의 전용 브랜치 이름 |
| 워크트리 | 구현·검사를 실행할 절대 경로 |
| 통합 대상 | 승인된 대상 브랜치 또는 미정 |

생성·재사용 근거는 [wk-worktree](../../wk-worktree/SKILL.md)의 실행 결과로 확인한다.
실제 생성은 현재 요청 범위에 승인된 구현 시작이 포함될 때만 수행한다.
논의·계획 단계에서는 예상 기준과 이름만 제안할 수 있다.
미생성 공간을 준비된 공간으로 기록하지 않는다.
공유 워크트리·브랜치는 하위 작업 완료와 별개로 정리 승인을 받아 제거한다.

## 커밋 후보

변경 단위는 한 가지 변경 이유로 설명할 수 있는 구현·테스트·문서의 묶음이다.
커밋 경계는 파일 수·실행자 수·경과 시간으로 정하지 않는다.
앞선 커밋 위에서 해당 단위가 일관되게 동작하는지 확인한다.

| 항목 | 내용 |
| --- | --- |
| 부모 `P` | 후보가 기반으로 삼은 현재 작업 브랜치의 전체 커밋 ID |
| 트리 `T` | 부모에 선택한 변경만 반영한 전체 파일 스냅샷의 Git tree ID |
| 변경 범위 | 한 가지 변경 이유·포함 파일이나 변경 부분·제외한 변경·선행 의존성 |
| 검증 위치 | 실제 검사에 사용한 위치와 그 소스가 `T`와 일치한다는 근거 |
| 검증 근거 | 해당 단위의 필수 검사·필요한 검토·환경·실제 결과·대상 `P`와 `T` |
| 생성 결과 | 실제 커밋 SHA·부모·트리·후보와의 동일성 판정·남은 변경 |

- 후보 준비는 커밋 생성과 구분한다.
- 검증 대상은 `P`와 선택한 변경으로 구성한 `T`다.
- 후보 밖의 미커밋·미추적 소스가 포함된 실행의 통과를 후보 검증으로 사용하지 않는다.
- 검증 환경의 의존성과 설정은 후보 소스와 구분해 기록한다.
- 검증 중 관련 입력이 바뀌면 영향받은 근거를 만료로 표시한다.
- 후보의 부모나 트리가 바뀌면 새 후보로 취급한다.
- 커밋은 실제 부모와 트리가 검증된 `P`·`T`와 일치할 때만 검증된 결과로 기록한다.
- 불일치한 커밋이 이미 생겼으면 실제 SHA와 차이를 남긴다.
- 불일치를 성공으로 처리하거나 이력을 임의로 다시 쓰지 않는다.
- 커밋 이후에도 아직 검증하지 않은 전체 목표와 남은 작업은 유지한다.

후보 준비·동일성 확인·커밋 생성 방법은 [wk-commit](../../wk-commit/SKILL.md)이 맡는다.
후보 검증 방법은 [wk-verify](../../wk-verify/SKILL.md)가 맡는다.

## 검증 근거

| 판정 | 의미 |
| --- | --- |
| 통과 | 확인한 결과가 조건을 충족한다. |
| 실패 | 확인한 결과가 조건과 다르다. |
| 판단 불가 | 근거가 부족해 조건 충족 여부를 결정할 수 없다. |
| 미실행 | 해당 확인을 수행하지 않았다. |

- 통과 이외의 판정을 통과로 합치지 않는다.
- 관련 내용이 바뀌면 영향받은 검증·검토 근거를 만료로 표시한다.
- `wk-work`는 현재 승인된 검증 범위에서 영향받은 검증·검토의 재수행을 배정한다.
- 수행 승인이 없거나 실행할 수 없으면 확인하지 못한 조건의 판정과 재개 조건을 기록한다.
- 만료된 근거는 재수행으로 유효성을 갱신하기 전까지 사용하지 않는다.
- 변경 단위 검증과 전체 목표 검증의 범위를 구분한다.
- 같은 `P`·`T`의 내용과 검증 조건이 유지되면 커밋 SHA가 생겼다는 이유만으로 같은 검사를 반복하지 않는다.

## 완료 판정

모든 완료 조건과 아래 작업별 요구를 충족한 경우에만 done으로 판정한다.

1. 완료 조건마다 산출물과 검증 근거의 유효성을 확인한다.
2. 미충족 조건이 있으면 남은 행동과 상태를 기록한다.

논의·계획에서 선택이 필요하면 [결정 준비](../../wk-decide/references/readiness.md#결정-준비)를 충족한 근거를 확인한다.
시간·비용 한도로 탐색을 끝낸 경우에는 [종료와 재개](../policies/progression.md#종료와-재개)에 따라 남은 미정을 기록한다.
문서 작성이나 탐색 한도 소진만으로 done으로 판정하지 않는다.
변경 단위의 커밋 완료만으로 전체 목표가 완료됐다고 판정하지 않는다.

| 작업 종류 | done에 필요한 근거 |
| --- | --- |
| 연구·논의 작업 | 합의한 질문의 답과 근거. 코드 실행·구현 작업공간 없이 끝낼 수 있다. |
| 계획 작업 | [계획 조율](../workflows/plan.md#단계-완료와-전환)의 완료 조건을 충족하는 설계·계약·실행 계획과 그 근거. |
| 하위 구현 작업 | 승인된 결과의 공유 구현 작업공간 반영과 해당 결과의 유효한 검증. 로컬 커밋이 범위에 있으면 확정 SHA도 연결한다. 별도 브랜치 병합은 요구하지 않는다. |
| 최상위 구현 작업 | 승인된 대상 브랜치 통합과 최종 결과의 유효한 검증. |

마스터 작업은 다음 조건도 확인한다.

- 필수 하위 결과가 남아 있으면 done으로 바꾸지 않는다.
- 하위 작업이 모두 done이어도 전체 완료 조건과 합류 결과를 따로 확인한다.
- 취소한 하위 작업이 있으면 마스터 작업의 범위와 완료 조건에 미치는 영향을 확인한다.
- 범위 축소가 필요하면 사용자의 확인을 받은 뒤 조건을 갱신한다.
