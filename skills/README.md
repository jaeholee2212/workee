# 소프트웨어 팩토리

- 결과물: 재사용 가능한 한국어 스킬과 작업 절차
- 사용자: 로컬에서 일하는 개발자 한 명
- 협업: 여러 에이전트와 여러 작업공간
- 제외: 런타임, 데이터베이스, 스케줄러, 전용 설치기

## 설치

Node.js와 npm(`npx` 포함)이 필요하다. 저장소 루트에서 실행한다.

```sh
make install
```

Skills CLI로 저장소의 모든 스킬을 사용자 공용 전역 경로(`~/.agents/skills`)에 설치한다.
설치 대상을 `universal`로 명시해 전역 설치를 지원하지 않는 에이전트의 오류를 방지하며,
확인 프롬프트 없이 설치한다.
다시 실행하면 현재 저장소 내용으로 재설치한다.

## 시작은 wk-work

개별 스킬을 고르는 대신 [wk-work](wk-work/SKILL.md)에 목표와 원하는 진행 범위를 말한다.

- “이 요청을 논의하자. 문제와 대안을 충분히 조사하고 방향을 제안해줘.”
- “합의한 방향을 설계하고 실행 계획으로 만들어줘.”
- “이 작업의 승인된 계획을 구현하고 검증해줘.”
- “이 마스터 작업이 실제로 끝났는지 확인해줘.”
- “이 작업을 이어서 하자.”

| 단계 | 다루는 질문 | 주로 조합하는 하위 스킬 |
| --- | --- | --- |
| 논의 | 무엇을 왜 해결하고 어떤 방향을 택할까? | wk-describe, wk-diagnose, wk-delimit, wk-compare, wk-decide, wk-review |
| 계획 | 어떤 설계로 해결하고 어떻게 나누어 구현·검증할까? | wk-plan, wk-compare, wk-diagnose, wk-decide, wk-contract, wk-coordinate, wk-review |
| 구현 | 어떤 변경 단위를 만들고 커밋 후보로 준비할까? | wk-worktree, wk-coordinate, wk-build, wk-commit |
| 검증 | 후보를 커밋할 수 있으며 전체 목표도 충족했나? | wk-verify, wk-review, wk-decide, wk-commit, wk-integrate |

단계는 고정된 직선 순서가 아니다.
`wk-work`가 기존 결과를 재사용하고 필요한 하위 스킬을 선택한다.
하위 스킬은 실제 작업 방법과 자기 결과의 완료 기준을 가진다.
`wk-work`는 반환된 근거·미정·필요 입력을 보고 후속 조사와 단계 전환을 정한다.
논의·계획에서는 [진행 정책](wk-work/policies/progression.md)에 따라 결정에 필요한 근거가 쌓일 때까지 탐색을 이어 간다.
탐색 중에는 [공동 탐구](wk-work/policies/collaboration.md)로 문제·대안·설계를 인간 파트너와 함께 검토한다.
함께 검토한 계획의 실행을 맡기면 그 범위에서 구현·검증·커밋을 자율적으로 진행한다.
기존 합의의 재사용과 직접 실행 조건은 [자율 진행과 사용자 판단](wk-work/policies/progression.md#자율-진행과-사용자-판단)에 둔다.
논의나 계획만 요청하면 그 결과를 남긴 뒤 멈춘다.
초안이나 조사 보고서만 요청하면 미합의 선택을 명시한 결과로 마칠 수 있다.
구현 중에도 검사하고 필요하면 논의나 계획으로 돌아간다.
위임받은 구현 범위에서는 변경 단위의 후보 검증과 로컬 커밋까지 자율적으로 진행한다.
사용자가 커밋을 제외했으면 그 제한을 따른다.
“이어서 하자”는 기존 승인 범위의 다음 행동을 실행하는 요청으로 다룬다.

탐색의 진척은 새 근거와 그 근거가 판단에 미친 영향으로 확인한다.
작은 가역적 선택은 필요한 차이만 확인한다.
설계를 바꿀 중요한 미정이 있으면 작업 분해 전에 조사한다.
접근 제한이나 실행 한도로 끝난 탐색은 결정 준비 완료와 구분한다.

## 한눈에 보는 작업 흐름

아래는 새 목표를 함께 논의하고 계획한 뒤 실행을 맡기는 기본 흐름이다.
`wk-work`가 현재 기록·합의·실행 위임에 맞춰 시작 단계와 다음 행동을 선택한다.

```text
사용자: 목표 + 요청 범위
   |
   v
wk-work: 현재 기록·합의·실행 위임 확인
   |
   v
[논의] <----> 인간: 문제·대안·판단 기준 함께 검토
   |
   +<------> 자율 조사·비교·실험과 새 근거로 반복
   |
   v  문제·범위·방향 합의
[계획] <----> 인간: 설계·사용 흐름·비용·검증 방법 함께 검토
   |
   +<------> 설계 가정 조사·비교와 피드백으로 반복
   |
   v  합의한 계획의 실행 위임
[구현 과정] ---> [전체 검증] ---> [요청 결과 완료]
     ^                |
     +----------------+  합의 안의 구현 보완

문제·설계의 중요한 전제가 바뀌면 해당 논의·계획으로 돌아간다.
```

- 논의·계획은 근거를 모으는 과정과 인간의 피드백을 주고받는 과정을 연결한다.
- 근거의 충분성·공동 검토·실행 위임을 각각 확인한다.
- 논의나 계획만 요청했으면 해당 결과의 완료 조건을 충족한 뒤 종료한다.
- 사용자 응답을 기다리는 동안에는 그 응답에 의존하지 않는 조사를 계속한다.
- 기존 계획에 유효한 합의와 실행 위임이 있으면 이를 재사용한다.
- 통합이 요청 범위에 포함되면 승인된 대상에 반영한 결과까지 검증한다.

실행을 위임받은 구현 과정에서는 의미 있는 변경 단위마다 다음 흐름을 반복한다.

```text
[구현·결과 회수] --> [후보 준비] --> [단위 검증] --> [로컬 커밋]
        ^             wk-commit       wk-verify       wk-commit
        |                                 |               |
        +----------- 검증 실패 -----------+               |
        +------------------- 다음 변경 -------------------+

필수 구현·허용된 커밋 완료 --> 전체 목표 검증 --> 요청 범위의 통합
```

후보는 부모 커밋과 선택한 변경만 반영한 전체 파일 트리로 고정한다.
단위 검증과 필요한 검토가 통과한 후보만 커밋한다.
실제 커밋의 부모·트리가 검증한 후보와 일치하는지도 확인한다.
단위 커밋의 완료와 전체 작업의 완료는 구분한다.

구현에서는 작업의 독립성과 분담 이점에 따라 실행자를 선택한다.
아래의 위임·진행 추적·결과 회수는 모두 `wk-work`가 조율한다.

```text
wk-work: 실행자 선택 + 진행 추적
   |
   +--> 작거나 강하게 결합된 변경 --> 직접 wk-build
   |
   +--> 독립적으로 분담할 결과 --> wk-coordinate: 범위·자원 배정
                                      |
                                      +--> 서브에이전트 A: wk-build
                                      +--> 서브에이전트 B: wk-build

각 결과 --> wk-work: 실제 변경 회수 --> 단위 검증·커밋 --> 전체 검증
```

선행 결과가 필요한 작업은 그 결과가 준비된 뒤 실행한다.
전체 검증은 합쳐진 결과를 `wk-verify`로 확인하고 필요한 `wk-review`를 조합한다.
각 단계의 결과·근거·남은 미정은 작업 기록에 남겨 다음 선택과 재개에 사용한다.

## 스킬 폴더 구조

```text
skills/
├── wk-work/
│   ├── SKILL.md                 # 진입점과 전체 조율 책임
│   ├── workflows/
│   │   ├── discuss.md           # 논의의 스킬 조합·전환
│   │   ├── plan.md              # 계획의 스킬 조합·전환
│   │   ├── implement.md         # 구현의 스킬 조합·전환
│   │   └── verify.md            # 검증의 스킬 조합·전환
│   ├── policies/
│   │   ├── progression.md       # 자율 반복·실행 권한·종료·재개
│   │   └── collaboration.md     # 공동 탐구·대화·피드백
│   └── references/
│       ├── work-model.md        # 실행 결과·작업 상태·관계·완료 계약
│       └── registry.md          # 기록과 보존 규약
├── wk-diagnose/SKILL.md         # 진단 방법과 자기 결과의 완료 기준
├── wk-compare/SKILL.md          # 대안 탐색·비교 방법
├── wk-commit/
│   ├── SKILL.md                 # 후보 준비·검증된 후보의 로컬 커밋
│   └── references/git-candidate.md # Git 후보 구성·실제 커밋의 일치
├── wk-decide/
│   ├── SKILL.md                 # 결정 방법
│   └── references/readiness.md  # 결정에 필요한 근거 평가
└── wk-*/SKILL.md                # 나머지 실무 방법
```

하위 스킬은 여러 단계에서 재사용하므로 단계별 폴더에 복제하지 않는다.
전체 흐름의 조율은 `wk-work`가 맡는다.
`wk-coordinate`는 배정된 작업 사이의 선행 산출물·작성 범위·공유 자원을 조정하는 하위 스킬이다.

## 함께 이해하고 실행을 맡기기

새 목표는 초기 조사로 얻은 사실·해석과 사용자의 경험을 대조하는 데서 시작한다.
LLM은 자율적으로 대안과 반례를 조사하고 중요한 발견을 대화에 가져온다.
사용자 피드백으로 달라진 문제·판단 기준·설계를 기록한다.
계획을 확정하기 전에 주요 사용 흐름과 실패 상황, 감수할 비용을 함께 검토한다.
대화의 깊이는 불확실성과 선택의 영향에 맞춘다.

처음의 포괄적인 “개선해줘”만으로 아직 검토하지 않은 설계를 구현하지 않는다.
계획에 대한 합의와 그 계획의 실행을 맡기는 요청은 구분한다.
“좋아” 같은 응답은 직전 대화의 대상과 범위에 연결한다.
LLM의 분석 완료나 설명 전달만으로 인간과의 합의를 기록하지 않는다.
기존 합의·실행 위임, 설계와 실행의 명시적 위임, 구체적으로 지시한 작은 수정은 진행 정책에 따라 재사용하거나 바로 실행할 수 있다.

실행을 맡긴 뒤에는 합의 안의 구현 세부·실패 보완·검증·단위 커밋을 자율적으로 진행한다.
중요한 전제가 바뀌면 영향받는 부분을 함께 재검토한다.
실제 대화 근거·합의와 이견·계획 버전·위임 범위는 [공동 검토와 실행 위임](wk-work/references/work-model.md#공동-검토와-실행-위임)에 남긴다.

## 작업 구조

- 작은 목표는 하나의 작업으로 진행한다.
- 분해가 필요하면 전체 목표를 가진 마스터 아래에 결과 단위의 하위 작업을 둔다.
- 단계는 작업의 진행 방식이고 상하위는 목표의 포함 관계다.
- 선행 의존성은 특정 행동에 필요한 산출물의 관계다.
- 하위 작업이 모두 끝나도 마스터의 전체 완료 조건은 따로 확인한다.

작업 ID, 파일과 이력은 [장부 규약](wk-work/references/registry.md)을 따른다.
단계, 상태, 관계와 완료 판정은 [공통 작업 모델](wk-work/references/work-model.md)을 따른다.

## 산출물 추적

작업의 현재 상태와 과정별 산출물을 구분해 보관한다.

```text
work/APP0001/
├── work.md
├── history.md
├── 261021/
│   ├── 001_diagnosis.md
│   └── 002_plan.md
└── 261022/
    ├── 001_verification.md
    └── 002_verification.stdout.txt
```

날짜·순번 할당, 수정본과 유효한 산출물 연결은 [산출물 저장 규칙](wk-work/references/registry.md#산출물-저장)을 따른다.

## 구현은 마스터 전용 공간에서

구현이 승인되면 [wk-worktree](wk-worktree/SKILL.md)가 전용 브랜치·워크트리를 준비한다.
최상위 마스터마다 하나를 만들고 모든 하위 작업이 같은 공간을 사용한다.
단일 작업은 자기 전용 공간을 사용한다.

기본 이름 예시:

```text
저장소: /projects/app
마스터: APP0001
브랜치: sf/APP0001
워크트리: /projects/app.wk-worktrees/APP0001
```

- 기준을 따로 지정하지 않으면 원본 프로젝트의 현재 HEAD 커밋을 사용한다.
- 논의·계획 단계에서는 공간을 생성하지 않는다.
- 미커밋 변경의 포함 여부가 미정이면 생성 전에 확인한다.
- 재개할 때는 기록된 브랜치·경로와 실제 Git 상태를 대조한다.
- 설정과 장부는 원본을 공유한다.
- 구현·검사는 전용 워크트리에서 수행한다.
- 같은 공간의 파일·Git 쓰기는 담당자를 조정한다.
- 하위 작업 완료를 위해 별도 브랜치 병합을 만들지 않는다.
- 최상위 작업의 통합·푸시·공간 제거는 승인 범위를 따로 확인한다.

사용자는 기존처럼 “승인된 계획을 구현해줘”라고 요청하면 된다.
작업공간 준비는 구현 진입 절차에 포함된다.

## 구현의 위임과 회수

서브에이전트를 사용할 수 있으면 독립적으로 구현·검사할 수 있는 결과를 적극 위임한다.
작거나 강하게 결합돼 분담 비용이 더 큰 변경은 직접 처리한다.
[wk-work의 구현 조율](wk-work/workflows/implement.md#실행자-선택)이 실행자 생성·진행 추적·결과 회수와 후속 배정을 맡는다.
`wk-coordinate`는 파일·계약·공유 자원의 배정을 정한다.
각 실행자는 `wk-build`로 담당 구현과 검사를 수행한다.
`wk-work`는 실제 변경을 회수한 뒤 합류 결과의 전체 검증까지 이어 간다.
개별 실행자의 완료 응답은 전체 목표의 완료를 대신하지 않는다.

## 의미 있는 단위로 커밋하기

계획에서 한 가지 변경 이유로 설명할 수 있는 잠정 커밋 단위를 잡는다.
필요한 구현·테스트·제품 문서는 함께 묶는다.
실제 의존성이 드러나면 `wk-work`가 경계를 조정한다.
파일 수나 서브에이전트 수에 맞춰 커밋을 나누지 않는다.

[wk-commit](wk-commit/SKILL.md)은 후보 준비와 검증된 후보의 커밋 생성을 맡는다.
그 사이에 `wk-work`가 `wk-verify`와 필요한 `wk-review`를 배정한다.
다른 미커밋 변경에 기대어 통과한 검사는 후보의 검증 근거로 사용하지 않는다.
Git 쓰기는 한 담당자가 수행하고 기존 사용자 변경과 staging은 보존한다.
각 커밋의 SHA와 해당 검증 근거는 작업 기록에 연결한다.
허용된 로컬 커밋마다 사용자에게 다시 묻지 않는다.
전체 목표 검증·대상 브랜치 통합·푸시는 각각의 범위와 조건을 따른다.

## 공통 기능과 직접 사용

- [wk-setup-workspace](wk-setup-workspace/SKILL.md): 최초 설정과 장부 가이드를 만든다.
- [wk-coordinate](wk-coordinate/SKILL.md): 작업 간 산출물과 작성 범위·자원 충돌을 조정한다.
- [wk-review](wk-review/SKILL.md): 논의나 변경안에 별도 검토가 필요할 때 사용한다.
- [wk-commit](wk-commit/SKILL.md): 변경 단위의 후보를 준비하고 검증된 내용으로 로컬 커밋을 만든다.
- [wk-integrate](wk-integrate/SKILL.md): 개발자가 승인한 통합을 수행한다.
- [wk-handoff](wk-handoff/SKILL.md): 중단과 담당자 인계를 기록한다.

하위 스킬도 직접 사용할 수 있다.
직접 요청하면 해당 스킬의 결과를 반환하고 다른 단계로 자동 확장하지 않는다.
`wk-work`와 하위 스킬은 같은 작업 기록을 사용한다.
전체 흐름을 사용하려면 `wk-work`와 위 표·공통 기능의 스킬을 함께 설치한다.
일부 하위 스킬만 설치할 때도 공통 규약을 제공하는 `wk-work`는 함께 설치한다.
필요한 스킬이 설치되지 않았으면 그 사실을 알리고 해당 절차를 임의로 대체하지 않는다.
