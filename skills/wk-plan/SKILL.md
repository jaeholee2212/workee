# 변경 계획

1. [장부 규약](../wk-work/references/registry.md)과 문제·선택한 방향을 읽는다.
2. [공통 작업 모델](../wk-work/references/work-model.md)을 읽는다.
3. 현재 작업과 상위 목표의 완료 조건·기존 계약을 확인한다.
4. [탐색 규약](../wk-work/references/exploration.md)에 따라 설계를 검토한다.

## 설계 구체화

- 사용자 목표를 달성하는 주요 사용 사례를 확인한다.
- 책임, 데이터, 상태, 판단과 외부 효과의 경계를 표시한다.
- 기존 구조를 유지하는 접근을 비교의 기준점으로 둔다.
- 기존 구조가 문제의 원인인지 확인한다.
- 선택에 영향을 주는 구현 방식은 [wk-compare](../wk-compare/SKILL.md)로 비교한다.
- 유력한 설계마다 같은 사용 사례와 중요한 실패 상황을 처음부터 끝까지 따라간다.
- 새 추상화가 필요하면 분리할 책임과 추가 비용을 설명한다.
- 결정 준비를 막는 가정은 제품 구현 전에 자료나 작은 실험으로 확인한다.
- 근거가 쌓인 선택은 [wk-decide](../wk-decide/SKILL.md)로 결정한다.
- 관찰 가능한 동작은 [wk-contract](../wk-contract/SKILL.md)로 계약에 반영한다.
- 문제나 방향이 바뀌면 영향받는 논의를 다시 연다.

설계와 계약의 [결정 준비](../wk-work/references/exploration.md#결정-준비)를 확인한 뒤 실행 작업을 나눈다.
조사가 남으면 질문·판별 방법·결과별 영향을 먼저 정한다.
실행할 수 있는 조사는 같은 요청 안에서 수행한다.

## 작업 분해

- 작은 변경으로 목표 전체를 검증할 수 있으면 단일 작업으로 계획한다.
- 독립적인 결과나 별도 담당 범위가 필요하면 현재 목표를 마스터로 두고 하위 작업을 나눈다.
- 각 하위 작업의 결과가 마스터의 어떤 완료 조건에 기여하는지 적는다.
- 하위 작업마다 범위, 완료 조건, 검사 방법을 정한다.
- 같은 목표의 기존 작업이 있으면 중복 생성 대신 연결 가능성을 확인한다.
- 하위 작업을 등록하면 포함 관계와 장부 색인을 함께 갱신한다.
- 등록만 한 하위 작업은 pending으로 기록한다.
- 선행 산출물마다 제공 작업, 준비 조건과 소비 시점을 적는다.
- 하위 결과의 합류 방법과 마스터 전체의 검증 방법을 적는다.

## 첫 실행

- 결정 준비를 막는 미정이 남으면 이를 판별하는 조사를 먼저 실행한다.
- 설계가 준비됐으면 사용자 행동을 확인하는 가장 작은 변경을 고른다.
- 변경 범위, 검사 방법, 필요한 선행 결과를 적는다.
- 구현 공간을 소유할 최상위 작업과 기준·통합 대상 후보를 적는다.
- 하위 검사가 통과해도 원래 문제가 남는 경우를 전체 검증에 포함한다.

## 산출물

계획은 [산출물 저장 규칙](../wk-work/references/registry.md#산출물-저장)에 따라 `plan` 용도의 파일로 남긴다.
완료 판정은 [계획의 완료 근거](../wk-work/references/plan.md#완료-근거)로 확인한다.
진행 권한은 [자율 진행과 사용자 판단](../wk-work/SKILL.md#자율-진행과-사용자-판단)을 따른다.
구현이 요청 범위에 있으면 준비된 첫 실행으로 이어 간다.
구현 작업공간은 구현 진입 시 [wk-worktree](../wk-worktree/SKILL.md)로 준비한다.
